## ⚠️ HEADLINE — THE PIVOT AS SPECIFIED IS A SHOWSTOPPER (do not queue R11 on the R9 edge)

The ladder edge **R9 (gcc-4.7.4) → R11 (gcc-10.5.0)** does NOT work, and no CXX flag fixes it.
gcc-10.5.0 **requires an ISO C++11 host compiler**, and gcc-4.7.4's C++11 is *experimental/incomplete*
(missing inheriting constructors, `thread_local`, etc. — the exact features gcc-10.5's source uses).
The corrected ladder needs an **intermediate gcc rung** (build gcc-4.8.5/4.9.4 with 4.7.4 first) OR a
**retarget of the pivot to gcc-10.4.0** (which still bootstraps from C++98 → 4.7.4 can build it directly).
Details in Q3 below. The draft build.sh/ncl are written to the R9 template as requested, but carry a
loud banner and a single `BUILDER_GCC` swap-point so the moment the intermediate rung exists, R11 flips
to it with a one-line change.

## Q1 — Does gcc-10.5 need newer gmp/mpfr/mpc than R8? → NO. R8 satisfies with huge margin.

gcc-10.5.0 `install.texi` "Tools/packages necessary for building GCC" documented minimums:

| lib | gcc-10.5 minimum | R8 ships | satisfies? |
|---|---|---|---|
| GMP  | **4.3.2** or later | **6.2.1** | ✅ (7 minor-series newer) |
| MPFR | **3.1.0** or later | **4.1.0** | ✅ |
| MPC  | **1.0.1** or later | **1.2.1** | ✅ |
| ISL  | 0.15+ (Graphite only) | — | N/A (see Q2) |

**Verdict: no new math rung.** R8's `/usr/lib/gcc-math` trio is reused verbatim via
`--with-gmp=/usr/lib/gcc-math --with-mpfr=… --with-mpc=…`, exactly as R9. (R8 already dropped its `.la`
files, so gcc links the static `.a` directly — no libtool-archive path games.)

## Q2 — Does gcc-10.5 pull in ISL (Graphite)? Can we avoid an ISL rung? → YES, avoid it. Flag: `--without-isl`.

ISL is **optional** — `install.texi` says it is *"Necessary to build GCC with the Graphite loop
optimizations"* and only references `--with-isl=PATH` to point at it. gcc's top-level `configure`
enables Graphite **iff ISL is found**; with no ISL in the tree it prints a note and builds without it.
The explicit, intent-documenting flag is **`--without-isl`** (autoconf's `AC_ARG_WITH(isl)`; gcc's
configure special-cases `with_isl=no` → Graphite disabled). There is **no** top-level `--disable-graphite`
flag in gcc-10.5 — `--without-isl` is the correct switch.

Crucially, **ISL is orthogonal to LTO**: `--disable-lto` disables `lto1`/the LTO front-end; it has
nothing to do with Graphite/ISL. So we can `--disable-lto` *and* `--without-isl` independently and add
**no ISL rung**. (Bedrock does no `-fgraphite`/`-floop-*` optimization; zero functional loss.)

**Verdict: `--without-isl` (belt) + never place ISL in the closure (suspenders). No ISL rung.**

## Q3 — THE U3 PIVOT: can gcc-4.7.4's g++ build gcc-10.5.0's C++ source? → NO. RISK = 🔴 RED / showstopper.

This is the load-bearing finding. Two independent, authoritative facts collide:

**(a) gcc-10.5.0 REQUIRES a C++11 host compiler — and this was BACK-PORTED into the 10.5 point release.**
The current GCC prerequisites doc (verified on two mirrors) states verbatim:
> *"Versions of GCC prior to 15 allow bootstrapping with an ISO C++11 compiler, versions prior to 10.5
> allow bootstrapping with an ISO C++98 compiler, and versions prior to 4.8 allow bootstrapping with an
> ISO C89 compiler."*

Parse: the C++11 requirement boundary sits **exactly at 10.5**. gcc-10.4 and earlier bootstrap from
**C++98**; **gcc-10.5 (through 14) require C++11.** The GCC 10 "Changes" note is blunt:
*"GCC 10.5 does not bootstrap with a C++98 compiler; if you need to start from C++98, you should build
10.4 or 9.5 instead."* So 10.5 is precisely the wrong version to hand a marginal C++11 host.

**(b) gcc-4.7.4's C++11 is EXPERIMENTAL and INCOMPLETE — below the documented minimum.**
GCC's own guidance is *"GCC 4.8.3 or newer has sufficient support for the C++11 features used"* to
bootstrap modern GCC; bootstrapping the modern series "requires a binary of GCC 4.8 or later." The GCC
4.7 C++0x-status page warns the 4.7 C++11 mode is experimental with no stability guarantee. The specific
killers that gcc-10.5's C++ source uses and 4.7 **cannot compile**:
  - **inheriting constructors** (`using Base::Base;`) — **added in gcc-4.8**, absent in 4.7 → hard error
    (`'X::X' names constructor`). This is the canonical, widely-reported 4.7-can't-build-modern-gcc wall.
  - **`thread_local`** — not fully in 4.7 (4.8).
  - assorted `<type_traits>` / ref-qualifier gaps (ref-qualifiers landed 4.8.1).

**Why `--disable-bootstrap` makes it WORSE, not better:** single-stage means the *host* g++ (4.7.4)
compiles **every** `.cc` in gcc-10.5 directly — there is no stage2/stage3 where a freshly-built modern
g++ takes over. Every C++11 gap in 4.7.4 is fatal on first contact.

**Does `-std=c++11` / `-std=gnu++11` as a CXX flag save it? → NO.** 4.7.4 *accepts* the flag (it's not a
parser problem), but the flag cannot conjure features the front-end never implemented. The build will
either be rejected at configure (if it probes a 4.8-only feature) or, more likely, die mid-compile on an
inheriting-constructor/thread_local use in gcc-10.5's source. This is a *capability* gap, not a flag gap.

**RECOMMENDED FIXES (pick one; both are drafted-for in the build files):**
  1. **Insert an intermediate rung** R9.5 = **gcc-4.8.5** (or 4.9.4) built BY R9 gcc-4.7.4. gcc-4.8.x is
     `< 10.5` → bootstraps from **C++98**, which 4.7.4 fully supports → 4.7.4 CAN build 4.8.5. Then R11
     is built by **4.8.5's g++** (the documented ≥4.8.3 minimum). This is the ladder-correct path and
     matches the GCC project's own "build an intermediate compiler" advice. Cost: +1 gcc rung.
     *(Ultra-safe variant: use gcc-9.5.0 as the intermediate — GCC itself recommends 9.5 — but that is a
     much bigger single rung. gcc-4.8.5 is the minimal insertion; 6.5.0/9.5.0 trade a bigger rung for
     rock-solid, non-experimental C++11 in the builder.)*
  2. **Retarget the pivot to gcc-10.4.0** (needs only **C++98** → 4.7.4 builds it *directly*, ZERO new
     gcc rung). Seal 10.4.0 as the pivot; climb 10.4 → 11+ later with 10.4's solid C++14 g++. Cost:
     mirror `gcc-10.4.0.tar.xz` (NOT currently in `gs://minimal-staging-archives/` — only 10.5.0 is) and
     re-pin. This is the **lowest-effort** fix (no new gcc rung at all) and arguably the cleanest: 10.4 is
     the last C++98-bootstrappable gcc, i.e. the natural bridge from a 4.7-class seed.

My recommendation: **Option 2 (retarget to 10.4.0) if a still-modern C++14 g++ pivot is acceptable**
(it is — 10.4 ≈ 10.5 minus bugfixes, and it removes an entire gcc rung). Fall back to **Option 1
(gcc-4.8.5 intermediate)** only if 10.5.0 specifically must be the sealed artifact.

## Q4 — Which musl-compat seds does gcc-10.5 need beyond siginfo/ucontext? → essentially NONE for our config.

gcc-10.5 (2023) POST-dates the musl/glibc header churn that forced R6/R9's seds, and our `--disable-*`
flags amputate the musl-hostile components:

- **`struct siginfo → siginfo_t` and `struct ucontext → ucontext_t`** (R9's two seds): **NOT NEEDED.**
  The `ucontext_t` fix (Joseph Myers, upstream commit `14c2f22`, 2017-06-27) shipped in **gcc-8+**; the
  `siginfo_t` fix is even older. gcc-10.5's `gcc/config/i386/linux-unwind.h` **already uses `ucontext_t`/
  `siginfo_t`.** Keep R9's `[ -f "$f" ] && sed …` as a *harmless defensive no-op* (it just won't match),
  but it is not load-bearing.
- **libsanitizer / libssp / libgo / libphobos / ada** — these carry the bulk of Alpine's musl gcc-10
  patch set (LFS64 symbols, `time_t` width, `struct sock_fprog` sizes, `sched.h` includes, non-C-locale
  exceptions, `libssp_nonshared.a`). We build **`--disable-libsanitizer --disable-libssp --disable-libgomp
  --disable-libquadmath`**, `--enable-languages=c,c++` only, `--disable-shared`, `--disable-lto` → that
  entire patch surface is **out of the build**. No seds required.
- **libstdc++ against musl** — WE DO build a static `libstdc++.a`/`libsupc++.a` (that's the point of the
  pivot). Alpine builds libstdc++ on musl unpatched for the common case; the residual patches are for
  edge features (non-C locales, `_GLIBCXX_USE_*` probes). Expect this to build clean under static; if a
  configure probe misfires, it will surface as a named failure — add a targeted sed then, not preemptively.
- **dynamic-linker / musl triple** — glibc's `/lib64/ld-linux-x86-64.so.2` default baked into specs is
  **inert** under `--disable-shared --static` (we never emit a dynamic executable). No `linux.h` sed
  needed. (See "triple decision" below for the cleaner-but-riskier alternative.)

**Verdict: keep R9's siginfo/ucontext seds as defensive no-ops; add NO new musl seds up front.** The R11
risk is the C++11 pivot (Q3), not musl compat.

## Other decisions baked into the draft

- **Tarball is `.tar.xz`** → closure swaps R9's `bzip2` for **`xz`** (R8 precedent). `tar --no-same-owner`
  (chown-hostile, the R8 wall).
- **Assembler = R10 binutils-2.41 (intended).** R10 is **not drafted yet** (sequencing gap — the ladder
  puts R10 *before* R11). The draft `build.ncl` imports **R5 binutils-2.30** (exists, handles x86_64
  fine) as a buildable stand-in, with a loud `TODO` to swap to `../stage0-binutils-2.41` once R10 lands.
  **R10 must be drafted + sealed before R11 can be real.**
- **Triple stays `x86_64-linux-gnu`** (consistency with sealed R6→R9 + the `-static`/sysroot-wrapper
  approach that's proven 4 rungs running). A `x86_64-linux-musl` triple would auto-select musl specs
  (musl dynamic linker, no glibc multilib osdirnames) and is arguably cleaner for a musl bedrock, but it
  deviates from the proven pattern and risks new config-path surprises. Flagged as a *future cleanup*,
  not adopted in the draft.
- **Outputs add libstdc++** — R9's outputs captured only `usr/bin/*`, `usr/libexec/**`, `usr/lib/gcc/**`.
  R11 also emits `libstdc++.a`/`libsupc++.a` (→ `usr/lib/*.a`) and the C++ headers (→ `usr/include/c++/**`).
  The draft adds both globs. **↳ Check R9: it may be silently dropping its own libstdc++.a** (latent bug
  worth a look — its g++ is useless downstream without the C++ std lib captured).
- **Model-B mtime guard + LOUD regen stubs** ported from R9/R6. gcc-10.5's generated-file set is larger
  than 4.7.4's (more `*.opt`→`options.c` via awk, gengtype output, `gengtype-lex.c` via flex, `intl/
  plural.c` via bison). The touch-list is broadened; the stubs fail loud and name any miss. **A local
  configure-probe of the extracted 10.5 tree is still advised before the first cloud build** (confirm the
  release tarball ships every generated file and needs no autoreconf/bison/flex) — same caveat as R9.
- **fixincludes no-op stub** — permanent gcc-rung pattern (musl headers are clean). `STMP_FIXINC=`.
- **`-j1`, 16G builder, warm RemoteCache, queue LAST/serial** — gcc-10.5 `cc1plus` is a bigger OOM/time
  pole than R9. `MAKEINFO=true` + `--disable-nls`.
- **gcc-cc / gcc-cxx wrapper** — R11 needs BOTH a C wrapper (CC, over 4.7.4's `gcc`) **and** a C++ wrapper
  (CXX, over 4.7.4's `g++`). The C++ wrapper uses `-nostdinc` (drops the coin-flip `/usr` C headers) +
  `-isystem $GI` (builder-gcc freestanding) + `-isystem $SR/include` (musl-1.2.5 C headers) but does
  **NOT** pass `-nostdinc++` — the builder-g++'s own libstdc++ headers (built against musl-1.2.5 in R9)
  must stay visible so gcc-10.5's `#include <vector>` resolves. Watch the C++ header search order
  (`#include_next <stdlib.h>` from `<cstdlib>` must reach musl, not glibc) — a predicted iteration point.
- **sha256 pin** = `25109543fdf46f397c347b52d8d7f298251990e99d47b6b6f0a643332d0d2beb` (matches the forward-map
  prefix `25109543fdf4`; the mirror is byte-identical so the sha is preserved). **Re-verify at pin time**:
  `gcloud storage cat gs://minimal-staging-archives/gcc-10.5.0.tar.xz | sha256sum`. (Search corroborated
  the SHA512 `d86dbc18…195bffd`; SHA256 was not independently locatable via public hash files — Buildroot
  master no longer carries 10.5.0 — hence the explicit pin-time check.)

## Predicted walls (ranked)
1. 🔴 **C++11 pivot (Q3)** — gcc-4.7.4 g++ cannot compile gcc-10.5's C++11 source; `--disable-bootstrap`
   guarantees first-contact failure (inheriting ctors / thread_local). **Blocker until an intermediate
   4.8.5/4.9.4 rung exists OR the pivot retargets to 10.4.0.** Everything below is moot until this is fixed.
2. 🟠 **Sequencing: R10 (binutils-2.41) not drafted** — R11's assembler rung is missing. Draft/seal R10
   first (or accept R5 2.30 as stand-in for a first bring-up).
3. 🟡 **Model-B completeness on the larger 10.5 generated set** — a regen stub may fire; broaden the
   touch-list per the named miss. Do a local configure-probe first.
4. 🟡 **libstdc++ static build against musl** — likely clean (Alpine precedent) but a configure probe
   could need one targeted sed; also ensure the outputs actually capture `libstdc++.a` + C++ headers.
5. 🟡 **C++ header search order in the CXX wrapper** — `-nostdinc` + keep-`-nostdinc++`; verify
   `<cstdlib>`→`<stdlib.h>` resolves to musl. Iterate against the first cloud build.
6. 🟢 **OOM / wall-time** — bigger than R9; `-j1`, 16G, warm cache, queue last.

## Observations (beyond scope, flagged per subagent guidance)
- **The forward map (`bedrock-r8-r11-forward-map.md`) omits the C++11 host-compiler constraint entirely.**
  It lists R9(4.7.4) → R11(10.5.0) as a clean edge and only hand-waves "does 4.7's g++ compile 10.5?" as
  "the last big unknown." It is not an unknown — it is a documented NO. The map (and the north-star
  ladder) should be amended to insert the intermediate gcc rung or retarget to 10.4.0 **before** any R11
  build cycle is spent. This is the single most important correction for B3.
- **R9's own output set looks like it drops `libstdc++.a` and the C++ headers** (`usr/bin/*` +
  `usr/libexec/**` + `usr/lib/gcc/**` only). If so, R9's g++ is shipped without a C++ standard library —
  which would *also* break any real use of it as R11's builder even after the C++11 issue is solved.
  Worth auditing R9's captured outputs against what `make install` actually wrote to `$OUTPUT_DIR/usr/lib`
  and `$OUTPUT_DIR/usr/include/c++`.
- **`--without-isl` + never-mirror-ISL is a permanent bedrock stance worth recording** in the reflexes
  list: bedrock does no Graphite, so ISL never enters the closure on any future gcc rung.
